# Replacing Atlas with Alembic

**Status: done.** This was the evaluation written before the switch; it is kept
as the record of why, and of what was measured. The resulting setup is documented
in `app/db/README.md`; the cutover runbook is the "Baseline strategy" section
below, and its step 2 is the part that still has to be run by hand against Neon.

Atlas's pgvector support is a **logged-in** feature, and the account's Atlas Pro
plan has expired. That is not a partial degradation: with `ATLAS_TOKEN` set, the
CLI refuses outright, and with it unset the *existing history* is unrunnable —
the `unify_symbols` migration carries txtar pre-migration checks, themselves a
logged-in feature. Both measured in a web session against the local dev cluster:

```
$ atlas migrate apply --dir file://migrations --url …
Error: login with environment variable ATLAS_TOKEN failed: Your Atlas Pro plan
has expired: logout or upgrade your plan

$ env -u ATLAS_TOKEN atlas migrate apply …
Error: migration checks (using atlas:txtar) are available to logged-in users
only, but found usage in: 20260721060312_unify_symbols.sql
```

So `apply-migrations.yml` is broken today, not just `diff`/`lint`. The database
is model-driven either way; what changes is the tool that plans and records the
SQL. This document is the evaluation of what an Alembic switch costs, with the
risky parts verified rather than assumed.

## What was verified

A full dry run in a web session, against Postgres 16 + pgvector on `:5433`:

1. Built a reference database by replaying all 47 Atlas migrations by hand
   (extracting the `-- migration.sql --` section from the txtar one) — 48 tables.
2. Scaffolded a throwaway Alembic env pointing `target_metadata` at
   `app.db.Base.metadata`, with `compare_type=True` and
   `compare_server_default=True`.
3. Autogenerated a single baseline revision from the models, applied it to an
   empty database, and diffed the two schemas via `information_schema` and
   `pg_constraint`.

**Result: columns, indexes and constraints are byte-identical** between the
Atlas-built schema and the Alembic-built one, once three gaps are patched (below).
`alembic check` then reports "No new upgrade operations detected" against *both*
databases — including the Atlas-built one after `alembic stamp head` and dropping
`atlas_schema_revisions`, which is exactly the production cutover.

The only residual difference is **physical column order**: Atlas appended columns
in the order its 47 migrations added them, a fresh baseline emits them in model
order. That is `attnum` ordering only — it affects `SELECT *` column order and
nothing else, and no code here selects with `*`.

### The three gaps in autogenerate

| Gap | Symptom | Fix |
|---|---|---|
| **Extensions** | Alembic never emits `CREATE EXTENSION`. The models attach `vector`/`pg_trgm` as `before_create` DDL events on the metadata — those fire for `create_all`, not for Alembic. | Two `op.execute("CREATE EXTENSION IF NOT EXISTS …")` at the top of the baseline. Permanent: any future migration adding an extension must hand-add it, same as under community Atlas. |
| **pgvector import** | The column renders as `pgvector.sqlalchemy.vector.VECTOR(dim=1536)` but no `import pgvector` is emitted → `NameError` on upgrade. | Add `import pgvector.sqlalchemy` to `script.py.mako`, or a `render_item` hook in `env.py`. One-time. |
| **`promoted_theorems` ⇄ `proofs` FK cycle** | SQLAlchemy warns "unresolvable cycles", drops those FKs from the sort, and autogenerate emits `create_table('promoted_theorems', …)` *before* `proofs`, `terms` and `formal_systems` exist. The baseline does not run. | One-line model change: `use_alter=True` on `promoted_theorems.proved_by_id`'s `ForeignKey`. Sorting then resolves — but `op.create_table` silently *skips* a `use_alter` FK, so the constraint must also be moved to an explicit `op.create_foreign_key` at the end of the baseline. `alembic check` catches it if you forget (it did). |

`Vector(1536)`, the HNSW index (`postgresql_using='hnsw'`,
`postgresql_ops={'embedding': 'vector_cosine_ops'}`) and all six `gin_trgm_ops`
trigram indexes render **correctly** with no help. `compare_server_default=True`
produced no false positives across the schema's 48 server defaults, and
`compare_type=True` none across `jsonb`/`uuid`/`vector` — so both can be on,
which is what keeps the drift check as sharp as Atlas's was.

`create_all` is unaffected by the cycle today (SQLAlchemy breaks it with a
post-hoc `ALTER` there), so the test suite and the `scripts/` helpers never saw
this. It is an Alembic-only defect.

## Baseline strategy: squash, don't port

Do **not** translate 47 Atlas migrations into 47 Alembic revisions. The models
are the source of truth, every deployed database is already at head, and the dry
run proves a single generated baseline reproduces the deployed schema exactly.
Port the *state*, not the history; git keeps the history.

Cutover, in order:

1. Land the `use_alter=True` model change and the Alembic scaffolding, with the
   baseline revision generated and hand-patched as above.
2. **Before merging**, against both Neon branches (`main` and `develop`), on the
   unpooled endpoint:

   ```bash
   MIGRATE_URL="$NEON_UNPOOLED_URL" uv run alembic stamp 18fbd4863856
   psql "$NEON_UNPOOLED_URL" -c 'DROP TABLE IF EXISTS atlas_schema_revisions'
   ```

   `18fbd4863856` is the baseline revision, and `alembic current` should print it
   afterwards. Without the stamp the apply workflow would try to `CREATE TABLE`
   on a populated database — it fails loudly rather than destructively, but it
   fails. Dropping Atlas's bookkeeping table is not cosmetic: it lives in
   `public`, so `alembic check` reads it as a table the models do not have.
3. Merge. `alembic upgrade head` is then a no-op on both, and the next model
   change generates revision two.

## CI: what each Atlas step becomes

### `migrations.yml` (PR gate)

The pgvector service container stays. `ariga/setup-atlas` and the `ATLAS_TOKEN`
secret go.

| Atlas step | Alembic replacement | Notes |
|---|---|---|
| `atlas migrate validate` (`atlas.sum` integrity) | `test "$(alembic heads \| wc -l)" -eq 1` | There is no checksum file to corrupt; the failure mode Alembic actually has is **two heads** from a branch merge. Cheap and catches the real hazard. |
| `atlas migrate diff drift_check` + dirty-tree check | `alembic upgrade head` then `alembic check` | Strictly better: Atlas's check proved the models matched the recorded SQL; this proves that *and* that every migration actually executes against a real pgvector Postgres. Exit code is the verdict — no `git status` heuristic, no stray file left behind on drift. |
| `atlas migrate lint --git-base` | *(no direct equivalent)* | The one genuine capability loss — see below. |

The drift step also removes a wart: `atlas migrate diff` writes a file as a side
effect, which is why AGENTS.md has to warn against running it as a probe.
`alembic check` is read-only by construction.

### `apply-migrations.yml` (post-merge)

`atlas migrate apply --url "$MIGRATE_URL"` becomes `alembic upgrade head`. Two
consequences:

- The job needs Python now. `env.py` imports `app.db`, which pulls in SQLAlchemy,
  pgvector and fastapi-users, so it needs the project's runtime deps — `uv sync
  --locked` plus a driver, not just a downloaded binary. Adds ~30s.
- **The URL form changes.** The `NEON_*_MIGRATE_URL` secrets are libpq-style with
  `&search_path=public` appended — that parameter is Atlas-specific, and neither
  libpq nor asyncpg accepts it. Either rewrite the secrets, or normalise in
  `env.py` (strip `search_path`, coerce the scheme to `postgresql+psycopg`). The
  `search_path` trick existed to hide Neon's `neon_auth` schema from Atlas's
  "connected database is not clean" check; Alembic reflects only the default
  schema unless `include_schemas=True`, so the problem does not arise. Keep the
  **unpooled** endpoint — DDL in a transaction still breaks under PgBouncer.

### `tests.yml`

Only the path filter's comment ("tools/ is Atlas's model loader") — the suite
builds schemas with `metadata.create_all` and never reads `migrations/`, so no
test changes at all. `tools/atlas/schema.py` is deleted outright: `env.py`
imports `app.db.Base` directly, so the double-registration workaround that file
exists for is moot.

Path filters in both migration workflows: drop `atlas.hcl` and `tools/atlas/**`,
add `alembic.ini`. Keep `migrations/**` by reusing that directory as Alembic's
`script_location` (`migrations/env.py`, `migrations/versions/`), which also keeps
every doc reference to "migrations/" true.

## What is genuinely lost

- **`atlas migrate lint`.** Destructive-change detection across every migration a
  PR adds. Nothing in the Alembic ecosystem replaces it directly — `squawk` lints
  SQL files, not Python revisions. Practical substitutes, in increasing cost: a
  CI grep for `drop_table`/`drop_column`/`alter_column` requiring an explicit PR
  label; a round-trip job (`upgrade head` → `downgrade -1` → `upgrade head`) that
  at least proves `downgrade()` is real; or nothing, on the argument that this is
  a single-maintainer repository where the diff is reviewed anyway. Recommend the
  grep — it is ten lines and catches the case that matters.
- **txtar pre-migration checks.** The "assert these tables are empty before
  destroying them" guards. In Alembic this is ordinary Python in the revision
  (`op.get_bind().execute(...)`, then `raise`), which is *more* expressive, not
  less. The single existing use disappears with the squash.
- **Schema-as-code lint rules** (naming conventions, etc.). Never configured here;
  the naming convention lives in `app/db/base.py` and is enforced by the models.

## Cost

One PR, roughly half a day. Dependency: add `alembic` to the `dev` group (or a
dedicated `migrations` group — but `env.py` imports the models, so the apply job
needs runtime deps regardless, and the separation buys little).

Docs to update, all mechanical: `app/db/README.md` (the whole "Migrations
(Atlas)" section and the Neon notes), `AGENTS.md`/`CLAUDE.md` (the migrations
section and the web-session Atlas provisioning note — the pre-provisioned
Postgres on `:5433` is still wanted, just for `alembic upgrade head` rather than
as an Atlas dev DB), `scripts/edifyce-dev`'s `migrate()`, and the docstring
mentions in `app/db/__init__.py`, `app/db/base.py`, `app/db/session.py`,
`tests/test_db_models.py` and `tests.yml`.

The net is a simpler pipeline with one fewer paid dependency, one fewer CI
secret, a strictly better drift check, and one real capability given up.
